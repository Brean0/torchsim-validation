# F007 — List initialization ignores requested dtype

**Evidence level:** measured API consistency failure. **Not an external physics comparison.** CPU device behavior is a control; accelerator transfer has not been executed in this evidence.

Initialize a two-atom float32 `SimState`. Call `initialize_state` with `device=cpu` and `dtype=float64`, first on that state and then on a list containing it twice. The single-state call returns **torch.float64**; the list call returns **torch.float32**. Both return CPU tensors. The same public dtype argument is honored on one supported input form and ignored on the other.

[The audited `initialize_state`, lines 1554–1610](https://github.com/TorchSim/torch-sim/blob/d6d8e9fc30129e01a05b551c2d71912821c9b68b/torch_sim/state.py#L1554-L1610) clones and calls `.to(device, dtype)` in its single-SimState branch, whereas the list-of-SimStates branch returns `concatenate_states(system)` directly. The source also indicates that device conversion is bypassed in that branch. The executed reproduction establishes the dtype discrepancy; this repository does not claim a measured CPU-to-GPU failure from a CPU-only run.

No ASE/JAX MD/LAMMPS/TorchMD API is invented as an equivalent reference. The meaningful oracle is consistency between two documented input forms to the same TorchSim initializer.
