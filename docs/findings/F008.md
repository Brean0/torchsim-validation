# F008 — Rejected Monte Carlo swaps leave model extras from the rejected proposal

**Evidence level:** measured returned-state consistency failure using a deterministic toy model. **Not an external physics comparison.**

The two particles have atomic numbers [1,2] and x coordinates [0,1]. Define per-atom `site_signal = Z*x` and energy `-sum(site_signal)`. Initial signal is **[0,2]**, energy **-2**. The sole possible swap gives energy **-1**, a positive change **+1**. At kT=1e-6, the floating-point Metropolis acceptance probability underflows to **0**.

After rejection, TorchSim returns the original positions and energy **-2**, as expected, but its cached `site_signal` is **[1,0]**, the rejected proposal's signal. Reevaluating the model on the returned positions gives **[0,2]**. Thus the state object contains mutually inconsistent geometry/energy and model extras.

[Audited `swap_mc_step`, lines 280–299](https://github.com/TorchSim/torch-sim/blob/d6d8e9fc30129e01a05b551c2d71912821c9b68b/torch_sim/monte_carlo.py#L280-L299) computes model output on proposed coordinates, reverses rejected swaps and restores rejected energies, then unconditionally stores model extras from the proposal output. The evidence isolates one rejected swap and one per-atom extra. It does not establish a universal failure of accepted swaps, every Monte Carlo method, or every external model.

An external simulation engine would introduce different move/state/extra APIs and is not needed to decide whether a cached output matches the returned state. The live oracle is a fresh model evaluation on that exact state; no fake equivalent library is claimed.
