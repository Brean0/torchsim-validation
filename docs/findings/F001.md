# F001 — Default direct-force accumulation doubles symmetric pair forces

Native ASE, LAMMPS, JAX MD and TorchMD calculations agree on the tested two-atom forces. TorchSim's default full-list `PairForcesModel` returns twice those values. Its existing energy-derived and half-list controls agree with the references, which narrows the discrepancy to the default direct-force accumulation path.

## Setup and result

The comparison uses each library's native Lennard-Jones interaction. Two atoms are placed at `(0, 0, 0)` and `(r, 0, 0)`, with epsilon=sigma=1, cutoff=2.5, no periodic boundaries, and CPU float64.

Force on the first atom along x, in normalized units `F*sigma/epsilon`:

| Engine or TorchSim option | r=1.1 | r=1.3 | r=1.5 |
|---|---:|---:|---:|
| ASE | -1.588095390 | 2.239979930 | 1.158028831 |
| LAMMPS | -1.588095390 | 2.239979930 | 1.158028831 |
| JAX MD | -1.588095390 | 2.239979930 | 1.158028831 |
| TorchMD | -1.588095390 | 2.239979930 | 1.158028831 |
| TorchSim `PairPotentialModel` control | -1.588095390 | 2.239979930 | 1.158028831 |
| TorchSim `PairForcesModel`, half-list control | -1.588095390 | 2.239979930 | 1.158028831 |
| **TorchSim `PairForcesModel`, default full list** | **-3.176190780** | **4.479959860** | **2.316057662** |

The four external references agree to approximately `1.6e-15`. The affected TorchSim option gives twice their force in both the repulsive and attractive cases. The second atom receives the opposite force; all y/z components are zero.

Native JAX MD also checks the original soft-sphere example. At distance 0.5 with epsilon=sigma=1 and alpha=2, its forces are -0.5/+0.5. The affected TorchSim path gives -1/+1. This is a second interaction-law check of the same root cause.

## Why full and half lists should agree here

A full neighbor list contains both A-to-B and B-to-A. A half list contains one entry for the pair. For a symmetric interaction, these are two ways of representing the same physical interaction and should produce the same atomic forces.

The accumulation rule must match the list:

- With a full list, each directed entry supplies its source atom's contribution once.
- With a half list, the single pair entry supplies both atoms' contributions once.

The affected path applies both-endpoint accumulation to both directed entries. Each atom receives its contribution twice. The full list itself is a valid representation; the discrepancy comes from how its entries are accumulated.

TorchSim's [existing full-list/half-list test](https://github.com/TorchSim/torch-sim/blob/d6d8e9fc30129e01a05b551c2d71912821c9b68b/tests/models/test_pair_potential.py#L210-L228) also requires the two results to agree for a symmetric force.

## Working controls and affected paths

The full-list `PairPotentialModel` starts from pair energies and obtains forces by differentiation. Its tested force accumulation agrees with the four external references. `PairForcesModel` starts from a supplied pair-force function; its existing half-list option also agrees for the tested symmetric forces.

The relevant source is [direct-force accumulation](https://github.com/TorchSim/torch-sim/blob/d6d8e9fc30129e01a05b551c2d71912821c9b68b/torch_sim/models/pair_potential.py#L580-L588), compared with [energy-derived accumulation](https://github.com/TorchSim/torch-sim/blob/d6d8e9fc30129e01a05b551c2d71912821c9b68b/torch_sim/models/pair_potential.py#L431-L441).

`ParticleLifeModel` inherits the same direct-force implementation and selects its full-list mode. That is another exposed entry point for this root cause. A separate five-engine ParticleLife comparison has not been performed. The exact factor of two is established for the symmetric forces tested here; asymmetric force functions require separate analysis.

## Reproduce

From the repository root, validate the saved evidence:

```sh
python3 scripts/run_force_comparison.py
```

Install the pinned engines and rerun the native calculations:

```sh
python3 scripts/run_force_comparison.py --setup --live
```

The checker verifies agreement between the references, both working TorchSim controls, the two TorchSim neighbor backends and the affected path's factor of two. Exit zero confirms those observations; it does not mean the audited implementation is fixed.
